# 库结构说明

这套目录是为了「一个仓库装下几十个小工具」而设计的。核心只有一条：**每个工具在 `src/` 下占一个文件夹，彼此不知道对方存在。**

## 目录职责

| 路径 | 放什么 | 不放什么 |
| --- | --- | --- |
| `README.md` | 库总览、工具清单表 | 单个工具的详细说明 |
| `WadeToolbox.slnx` | 所有工具项目的聚合解决方案 | — |
| `.github/workflows/` | 每个工具一条 `ci-<工具名>.yml` | 跨工具的合并流水线 |
| `docs/` | 跨越所有工具的规矩：结构、新增流程、共享约定 | 单个工具的使用手册 |
| `src/<工具名>/` | 该工具的全部源码、测试、自己的 `docs/`、自己的 README | 别的工具的代码 |
| `src/_template/` | 新工具起点，复制走之后不用还原 | 真实业务代码 |

## 三条硬规矩

### 1. 工具之间不互相引用

`src/WorkEnc/` 不能 `ProjectReference` 到 `src/其他的/`。

需要共享代码时，**复制那 200 行过去**，而不是抽一个公共库出来。
理由：小工具的生命周期是「写完用半年，然后不动了」。公共库一改动就要连带回归所有工具，维护成本远大于复制的成本。

> 唯一例外：如果确实有三处以上在用的稳定逻辑（比如 `AtomicFile` 原子写），再考虑抽 `src/shared/`。抽之前先问自己：这玩意儿一年会改几次？

### 2. 每个工具自带测试项目

命名 `<工具名>.Tests`，放 `src/<工具名>/<工具名>.Tests/`。
测试是唯一能防止「三个月后回来改一个数字，结果把发工资算错」的东西。

### 3. 数据不落仓库

运行数据一律写 `%APPDATA%\<产品名>\`：

```
%APPDATA%\WorkEncourager\settings.json
%APPDATA%\WorkEncourager\history.json
%APPDATA%\WorkEncourager\app.log
```

仓库里的 `.gitignore` 已经挡住 `*.log` / `settings.json` / `data/`，但即便如此也不要往仓库目录里写数据——仓库随时可能被 `git clean`。

## 版本号规则

每个工具**独立版本号**，写在各自 csproj 的 `<Version>` 里，互不同步。

标签格式 `v<版本>` 会造成歧义（是哪个工具的 v2.2.2？），所以多工具之后改成：

```
workenc-v2.2.3       上班鼓励器
<工具名>-v0.1.0       新工具
```

现有 `ci-workenc.yml` 里的发版判断是按 `v*` 标签写的，等真的加第二个工具时再改成 `workenc-v*`。

## 命名约定

| 对象 | 规则 | 例子 |
| --- | --- | --- |
| 源码文件夹 | PascalCase，中文产品名对应一个英文短名 | `WorkEnc`、`TableDiff` |
| csproj 文件名 | 跟文件夹名一致 | `WorkEncourager.csproj` 例外，保留历史名 |
| 程序集名 | 发布出去的 exe 名 | `WorkEncourager.exe` |
| 测试项目 | `<源码项目>.Tests` | `WorkEnc.Tests` |
| CI 文件 | `ci-<源码文件夹小写>.yml` | `ci-workenc.yml` |
| 数据目录 | `%APPDATA%\<产品名>` | `%APPDATA%\WorkEncourager` |
| 仓库名 | 固定 `WadeToolbox`（工具箱名 ≠ 工具名），本地目录同名 | `zdhzhongtao/WadeToolbox` |

中文产品名用于界面标题、README 标题、Release 说明；英文名用于代码、路径、文件名。两边不要混。
