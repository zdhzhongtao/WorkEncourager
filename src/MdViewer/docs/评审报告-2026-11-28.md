# Markdown 阅读器 MdViewer 评估报告

- 评审对象：`src/MdViewer`，v0.5.3（csproj `0.5.3`，HEAD `077f537`）
- 评审日期：2026-11-28
- 评审方式：通读全部源码（71 个源文件 / 约 16.5k 行，不含 vendor 3.1MB）+ 跑单测 + 真机跑 GUI + headless Chromium 复现页面脚本问题 + 竞品调研
- 一句话结论：**定位选对了，工程底子也不差；但"能演示"和"能当日常主力"之间还差一批真实 bug，其中 2 个是阻断级、12 个是常用功能级（含 1 个"GBK 文档全乱码"的硬伤）。竞品的窗口期在收窄，建议先花 2 周把 P0/P1 清掉，再谈加功能。**

| 方面 | 评价 |

### 1.2 核心判断

**"还有没有 bug？"——有，而且不少，并且集中在最难被单测覆盖的那一层。**

- Core（渲染、清洗、EPUB、设置）测得比较扎实，问题少；
- 页面脚本（`app.js`）和 WPF 壳（`MainWindow.*.cs`）几乎没有自动化测试，**本次发现的阻断级问题全部落在这两层**；
- 现有的 `--snapshot` 自检只验证"静态渲染对不对"，验证不了"按键有没有反应、状态有没有还原、通知看不看得见"。这次抓到的几个大问题，恰好都是静态截图看不出来的。

### 1.3 必须先修的 5 件事（详见第三、四章）

1. **正文一被点过，整套快捷键就失效**：Ctrl+F / F5 / F11 / Alt+← / Ctrl+Shift+* 全部没反应（已用真机 + 截图逐帧对比证实）。
2. **标注超过一条就错位或丢失**：同段第二条高亮直接不见，不同段落时第二条会包到别的词上（已在 Chromium 里复现，真机可复现）。
3. **切换一次主题，全文 Mermaid 图永久退化成源码**，只能关掉文档重开（已复现）。
4. **导出与打印失真**：打印/导 PDF 时长代码行右侧被静默裁掉；导出 HTML 丢公式、丢 Mermaid、丢代码高亮、丢自定义字体。
5. **卸载后 `.md` 关联被写坏**：`install.ps1 -Uninstall` 把默认值写成空串，双击 .md 变成"选择打开方式"。

另外还有 4 个高影响、低成本的问题：**GBK/GB2312 编码的文档全部乱码（兜底代码页写错，功能从未生效）**、**Toast / "正在解析 EPUB" 被 WebView2 盖住永远看不见**、**F11 退出后宽屏和目录状态不还原**、**`Ctrl+Shift+E` 被 `Ctrl+E` 抢先命中（即使修好键盘也打不开外部编辑器）**。

### 1.4 评分卡（主观，但按本次证据打分）

| 维度 | 分数 | 依据 |
| --- | --- | --- |
| 功能完整度 | 7.5 / 10 | 阅读器该有的基本都有，缺 PDF、缺库级搜索 |
| 稳定性 | 4 / 10 | 10+ 个常用路径有真实缺陷，含 2 个阻断级；标注、快捷键属于"一用就中" |
| 代码质量 | 7.5 / 10 | 分层清楚、命名好、注释真实；但状态分散、异常宽泛、UI 层无测试 |
| 性能 | 7 / 10 | 渲染快（2.7MB/0.6s）；单文档 400MB 是架构代价 |
| 文档 | 7 / 10 | 三件套齐全、踩坑记录有价值；版本/功能描述已过时 |
| 竞品竞争力 | 6.5 / 10 | 有三个真差异化点，但 SumatraPDF 正在快速逼近 |

### 1.5 竞品一句话

市面上的"阅读器"要么只读 Markdown（Typora / MarkText / VS Code），要么只读 EPUB/PDF（Calibre / Thorium），**能在一个窗口、同一套主题里读 .md 和 .epub 的免费 Windows 工具确实不多**；但 **SumatraPDF 3.7 预发布从 2026-06 起已经补齐 Markdown、Mermaid、EPUB 脚注、朗读、批注、标签组**，它是本产品最直接、也最危险的替代品。本产品真正的护城河只剩三样：**双格式同窗、批注不写回源文件、长图分享**。

## 三、Bug 清单（按严重度）

> 严重度定义：
> **P0** = 核心功能不可用或数据/笔记错误，用户会认为"这功能是坏的"；
> **P1** = 常用路径明显错误，或可被外部文档触发的安全/完整性问题；
> **P2** = 边界场景 / 次要功能；
> **P3** = 打磨项，不影响正确性。
>
> 证据标注：**【实测】** = 本次真机或 Chromium 复现；**【代码】** = 读码确认，逻辑必然；**【疑】** = 读码/文档推断，未完全证实。

### 3.1 P0（2 个）

#### P0-1 正文获得焦点后，所有窗口级快捷键失效

- **位置**：`MainWindow.xaml:10`（`PreviewKeyDown="Window_PreviewKeyDown"`）、`MainWindow.Commands.cs:535-588`
- **触发**：打开文档 → 在正文里点一下（WebView2 拿到键盘焦点）→ 按 Ctrl+F / F5 / F11 / Ctrl+T / Ctrl+P / Alt+← / Ctrl+Shift+R…
- **现象**：**没有任何反应**。快捷键只在焦点还在工具栏/侧栏等 WPF 控件上时有效。
- **实测证据**：
  - 用 `GetGUIThreadInfo` 确认焦点在 `Chrome_RenderWidgetHostHWND`（WebView2 的原生子窗口）；
  - `PrintWindow` 逐帧对比：按下 Ctrl+F、F11、Esc 前后四张窗口截图的 SHA256 **完全相同**（无搜索条、无全屏、无退出）；
  - 代码全仓没有订阅 `CoreWebView2Controller.AcceleratorKeyPressed`，`app.js` 也没有把按键转发回宿主。
- **根因**：WebView2 是 `HwndHost`（原生子窗口），键盘消息进的是 Chromium 自己的窗口，不会冒泡到 WPF 的 `Window.PreviewKeyDown`；而程序又设置 `AreBrowserAcceleratorKeysEnabled = false`，浏览器侧也不处理，按键就此"消失"。
- **修复建议**（任一即可，推荐 1 + 3）：
  1. 订阅 `View.CoreWebView2Controller.AcceleratorKeyPressed`，在回调里把按键映射成命令，并置 `Handled = true`；
  2. 在 `app.js` 里 `keydown` 拦截 Ctrl/Alt/F 功能键，`postMessage` 回宿主（注意中文输入法）；
  3. 兜底：给常用命令加 WPF `InputBindings`（只能覆盖 WPF 焦点，不能解决正文焦点）。
- **顺带**：修改后必须补一组"焦点在正文时快捷键仍生效"的回归测试（可用 UI Automation 或录制式脚本）。

#### P0-2 两条以上标注时，高亮错位或整条丢失

- **位置**：`app.js:467-482`（`segments`）、`app.js:520-556`（`applyAnnotations`）
- **触发**：同一篇文档里有 ≥2 条标注（高亮/批注），重开文档或用侧栏增删标注触发重放。
- **现象**：
  - 同一段落两条：只有第一条出现，第二条**整条消失**；
  - 不同段落两条：第二条会包到**前一段的字符**上（复现为把 `"gamma "` 里的 `"mma "` 包住）；
  - 真机两条标注时，第一条覆盖范围扩大、段间出现一条 2px 的"高亮竖线"（零宽 mark）。
- **实测证据**（headless Edge + 真实 `app.js`）：
  - `case1_marks = [{id:"A", text:"The quick"}]` —— B 不见了；
  - `case3_p1 = <mark E>alpha</mark> beta ga<mark F>mma </mark>delta` —— F 本该在第二段 `zeta`；
- **根因**：`applyAnnotations` 只在开头取一次 `nodes` 快照；`wrapSegments` 里 `splitText` 把文本节点拆开后，后续 `segments(nodes, start, end)` 仍在用**旧节点集合 + 新节点长度**累计偏移，坐标系错位。`quote` 兜底又用旧 `whole` 去 `segments` 新节点，错上加错。
- **修复建议**：
  - 每条标注应用**前**重新 `textNodes()` 并重新定位（O(n·m) 对 2000 条上限尚可），或
  - 改为一次性扫描：把所有标注区间按起点排序，单次 TreeWalker 分段包 `<mark>`（推荐，O(n+m)），并处理重叠/相邻区间。
  - 补测：同段 2 条、跨段 2 条、重叠 2 条、嵌套节点（粗体/链接/代码内）各一条。

## 四、架构性问题（不是单点 bug，建议一起考虑）

### 4.1 键盘输入没有"跨 airspace"的方案

P0-1 不是漏了一个快捷键，而是**架构缺一层**：只要正文是 WebView2，WPF 的 `PreviewKeyDown` 就收不到键。同类产品（Markdown Monster 也是 WPF+WebView2）都在 `AcceleratorKeyPressed` 上做统一映射。建议做一个 `ShortcutRouter`：WebView2 事件 → 命令表 → 与 WPF `InputBindings` 共用同一张表，并补"焦点在正文时"的自动化回归。

### 4.2 WPF 覆盖层与 WebView2 的 airspace

Toast、BusyPanel、WelcomePanel 都在 WebView2 同一个 Grid 里。现在靠"隐藏 View"来让欢迎页可见（`ShowWelcome` 里手动 `View.Visibility = Collapsed`），但 Toast 无法这么做。可选方案：
1. Toast 改成独立无边框 `Window`（`AllowsTransparency` + `Topmost`），最简单可靠；
2. 升级到 `WebView2CompositionControl`（WPF 合成控件，支持 WPF 内容叠加，但需要 .NET 8+ 与 GPU 合成，改动大）；
3. 状态信息改走状态栏（放弃浮层）。

### 4.3 状态分散在多处，互相打架

同一件事有好几个"真相"：`TocToggle.IsChecked` vs `Settings.TocVisible` vs `_tocBeforeWide`；`_zen` vs `Settings.WideMode`；`_speakState` vs 页面 `speech` 状态；`_restorePending` vs `RememberScroll` 的异步续体。本次多个 P2（目录宽度回弹、F11 不还原、设置不生效、位置被清零）都是这个模式的表现。建议做**单向状态流**：设置是唯一真相，UI 只订阅；临时覆盖（zen/宽屏/定时换肤）进一个显式的 `ViewState` 对象，退出时整体回滚。

### 4.4 页面端数据模型不适合"增量编辑"

标注用"字符偏移 + 原文"存，遇到 DOM 变换（拆分文本节点、Mermaid 替换、表格排序）必然漂移。短期按 3.2 的建议重写重放算法；中期建议：
- 标注存"锚点四元组"（前文 20 字 + 选中文字 + 后文 20 字 + 近似偏移），重放时用"最近匹配"而不是全局第一次出现；
- EPUB 批注改用 CFI（Readium/Thorium 的做法），否则换字号/重排后必然漂。

### 4.5 测试结构错位

221 个测试全在 Core；出问题的 WPF 壳与 `app.js` 零测试。`--snapshot` 只能验证静态渲染。建议：
- 把 `app.js` 的核心逻辑（标注重放、表格排序、TTS 状态机、主题切换）抽成可被 Node 直接 require 的模块，用 Vitest/Jest 跑；
- WPF 壳用 `--self-test` 命令行钩子驱动关键流程（打开→改文件→切标签→关窗），断言 settings/notes 的最终状态；
- 至少给"标注 2 条""快捷键""主题切换后 Mermaid"补回归。

### 4.6 安全边界要写清楚

本程序处理的是"可能来自外部"的 md/epub。当前 CSP + 正则清洗能挡住脚本执行，但：
- `style="..."` 未清洗 → 文档可以伪装 UI（例如盖一个"请输入密码"的层）；
- 相对链接可直接启动本地 exe → 建议加白名单（只允许 `http/https/mailto` 和"本程序能打开的文档"），其余弹确认；
- 导出 HTML 没有 CSP（有意为之，方便看在线图），但用户会把它发给别人 → 至少保留 `script-src 'none'` 或提示"导出页不含脚本"。

### 5.3 我们真正的位置

**领先（别人结构性不做 / 没做）**

1. **Markdown + EPUB 同窗、同一套主题/字体**。免费阵营里 Typora / MarkText / Zettlr / MPE 都不原生读 EPUB；Calibre / Thorium / Okular 不原生读 Markdown。Sumatra 是唯一同时吃两边的，但它的 Markdown 只有几个月历史。
2. **批注存在 `notes.json`，不改源文件**。对"只读文档 + 要留批注但不能动文件"的场景（合同、规范、评审稿）很干净。Calibre 会写回 EPUB，Obsidian 只有 `==`，Typora/Zettlr 没有批注概念。
3. **整页长图导出**。竞品里只有 Typora、MPE、Sumatra（转图片）有类似能力，且少有"按当前主题 + 公式 + 图表一起出图"。
4. **阅读态细节**：20 套主题、三槽字体、护眼/报纸衬线/高对比、定时换肤 —— 比多数"附带一个 preview"的工具用心。

**持平（2026 年的入场券，不值得当卖点）**

GFM 渲染、代码高亮、目录、文件树、多标签、自动重载、最近列表、导出 PDF。

**落后（按痛感排序）**

1. **没有 PDF 阅读**。这是阅读器品类最致命的缺口；WebView2 自带 PDF 查看器，接入成本最低。
2. **没有跨文件/库级搜索**。只能文件树里翻，是"当主力"与"当玩具"的分水岭。
3. **单文档 400MB+ 的内存模型**。多开 3–4 个文档就 1.5GB；Sumatra 是原生渲染，量级低一个数量级。
4. **EPUB 只是"能读"**：无分页/双栏、出版社 CSS 全丢、批注用字符偏移（换字号会漂）。
5. **导出质量**：PDF 无书签/页眉页脚、代码截断；HTML 丢公式图表；无 EPUB/DOCX 导出。
6. **可访问性无证据**（屏幕阅读器语义、焦点可见、高对比）—— 进政企/教育是硬门槛。

### 5.4 定位建议

不要试图在"广度"上赢 Obsidian（插件/同步）、Calibre（书库/转换）、Sumatra（PDF 全家桶）。胜算在**窄而深**：

> **"中文技术文档的双格式阅读器"**：.md 与 .epub 同窗同主题、公式图表完整、批注不污染源文件、一键长图分享、离线零依赖。

这三件事恰好是大厂不愿做、个人开发者做得动的"小而烦"。

## 八、给决策者的一句话

**这个工具已经过了"能不能用"的阶段，现在是"敢不敢当默认阅读器"的阶段。** 把 2 个 P0 和 12 个 P1 清掉（约 2 周），它就能稳定替代"用 VS Code 看 md"；再补 PDF + 库级搜索（约 1–2 个月），它才配叫"日常主力"；之后守住"双格式 + 批注 + 长图"这三件事，不要跟 Obsidian 比生态。
