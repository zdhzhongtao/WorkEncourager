# 表格比对器 · 开发记录

> 记录这个工具怎么来的、每个技术决策为什么这么定、踩了哪些坑。
> 使用说明见 [使用说明.md](使用说明.md)。

---

## 需求

财务对账场景：月初拿到「系统导出的表」和「业务给的表」，要人工找出三件事——多了哪些行、少了哪些行、哪些字段被改过。原来靠 Excel 的 `VLOOKUP` + 眼睛扫，几百行就开始漏。

硬要求（来自 `docs/四个小工具开发规格.md` 第 5 节）：

- 上下两个文件槽，拖放 + 浏览，支持 `.xlsx .xlsm .csv .tsv`
- 三种比对方式：按主键（1~3 列复合）/ 按行位置 / 按整行内容
- 列映射 + 忽略列；忽略大小写 / 首尾空格 / 空串等价 / 全空行 / 数值容差
- 结果：行级状态 + 单元格级高亮，`旧值 → 新值`
- 导出 CSV（带 BOM）与 xlsx（汇总 + 明细，保留高亮）
- 5 万行 × 50 列不卡界面，可取消

## 关键决策

### 1. 单元格统一存成「规整后的字符串」，不做类型系统

原始想法是保留 `object` + 类型标记，比对时按类型走分支。实际写下来发现没必要：用户关心的是「显示出来一不一样」，而且 Excel 里的数字和 CSV 里的文本常常是同一个业务值（`1000` vs `"1000.00"`）。

最终做法：读表时就把单元格转成文本并规整——

- 数字用 `"0.###############"` 格式化，`1.2000000000000002` → `1.2`（浮点尾巴来自 Excel 的双精度存储）
- 日期用 `yyyy-MM-dd`，带时间的补到分钟
- 比较时再用 `CellText.Canonical` 归一：能解析成数字的统一成数字文本，这样 `1000` 和 `1000.00` 天然相等

代价：丢掉「这一列本来是日期还是文本」的信息（所以文本格式的 `45292` 不会自动变日期）。换来的是整个比对引擎没有类型分支，测试好写。

### 2. 数值容差只在容差 > 0 时才走浮点比较

容差 0（默认）时走的是**规整文本比较**，不是 `double` 相等。原因：`0.1 + 0.2` 那套浮点误差会让「肉眼一样」的两个数被判成不同。规整成文本后 `1000.1` 就是 `"1000.1"`，稳定。

容差 > 0 时才 `Math.Abs(a - b) <= tolerance`，这才是用户填 `0.01` 想表达的「一分钱以内算一样」。

### 3. 主键重复：警告 + 按第一条匹配，绝不静默

第一版实现里 B 侧重复主键直接 `index[key] = i` 覆盖，等于只留最后一条，用户完全看不见。现在改成 `Dictionary<string, List<int>>`，比完把两侧计数一合并，任何一侧出现 >1 次就进 `DuplicateKeys`，界面汇总条弹「主键重复 N 处」，点开列出具体键值。

**这是个诚实性问题**：解释不了「为什么这两行没比出来」比算错更糟。

### 4. 结果表用「按列下标绑定的数组」而不是每单元格一个对象

5 万行 × 50 列 = 250 万个单元格。如果每个单元格一个带 `Brush`/`Text`/`Tip` 的对象，光对象头就 100 MB+，滚动会卡。

最终 `RowView` 只持有三个平行数组：`Text[]`（显示的字符串，大部分是源数据的引用，不复制）、`Tip[]`、`Bg[]`（画刷）。没差异的行共享同一个空画刷数组，只有真正有修改的行才新建 `Bg` 数组。

DataGrid 列是运行时生成的 `DataGridTemplateColumn`，模板字符串用 `XamlReader.Parse` 拼下标：

```xml
<Border Background="{Binding Bg[3]}">
  <TextBlock Text="{Binding Text[3]}" ToolTip="{Binding Tip[3]}" />
</Border>
```

没用 `FrameworkElementFactory`（微软早就建议别用，而且 50 列解析 XAML 也就几十毫秒，一次性开销）。

### 5. 红黄绿在这里是 diff 语义，不是涨跌语义

`docs/共享约定.md` 规定金额涨跌用「涨红跌绿」。本工具**故意不用**那套：

| 状态 | 颜色 | 理由 |
| --- | --- | --- |
| 差异单元格 | 黄底 `#FEF3C7` + 深黄字 | 黄=注意，跟股市无关 |
| 仅A有 | 红字 `#DC2626` | 红=缺失/告警 |
| 仅B有 | 绿字 `#16A34A` | 绿=新增 |

在开发记录里写清楚这个例外，避免以后有人「顺手统一一下」把语义搞反。

### 6. 导出 CSV 与 xlsx 共用一份「摊平」逻辑

`CsvDiffExporter.EnumerateLines` 把 `DiffResult` 摊成 `List<DiffLine>`，CSV 和 xlsx 都吃这个列表。好处是两边行数、行序永远一致（有测试守着），坏处是 xlsx 想加个 CSV 没有的列就得改摊平逻辑——可以接受。

### 7. 主题走 `DynamicResource` + 运行时注入

`Theme.ToResourceMap()` 把 30 多个颜色刷进 `Application.Resources`，XAML 里写 `{DynamicResource ThemeAccent}`。切换主题不需要遍历控件树，也不需要重启。

代价：`DataGrid` 的单元格背景是在代码里直接赋 `Brush` 的，切主题时必须 `Render()` 重建一遍（`ThemeButton_Click` 里就这么做的）。为此把「重建结果表」和「重新比对」拆开了——重建只花几十毫秒。

## 踩过的坑

| 现象 | 根因 | 修法 |
| --- | --- | --- |
| B 侧重复主键不报警 | `seenA.ContainsKey(key)` 就跳过，把「A 有 B 也有」的重复键吞了 | 改成两侧所有键取并集再逐个看计数 |
| 按整行内容：明明一样却全报「仅A有」 | 匹配后只把计数减到 0，最后补「仅B有」时按计数判断，0 也算未匹配 | 改成 `bool[] usedB` + 每个签名一个候选下标列表 |
| BOM 测试一直失败 | `new UTF8Encoding(true).GetBytes()` **不带** BOM，只有 `File.WriteAllText` 才会写 | 测试里手动拼 `EF BB BF` 三个字节 |
| xlsx 里 `File.Move` 偶尔失败 | ClosedXML 的 `SaveAs` 还持有文件句柄 | 先 `SaveAs(path + ".tmp.xlsx")`，`using` 结束（句柄释放）后再 `File.Move` |
| `.xls` 读出来全是乱码 | ClosedXML 只支持 OpenXML 格式 | 明确拒绝，提示另存为 xlsx |
| 中文 CSV 读成乱码 | 默认编码是 UTF-8 | 严格 UTF-8 解码失败 → 退 `GB18030`（需 `Encoding.RegisterProvider`） |
